# NAVIAR Passport Intelligence v0.2

Экспериментальное локальное извлечение данных тестового паспорта. Это не проверка подлинности, юридической действительности или миграционных правил.

## Архитектура

- models.py: контракты OCRProvider, OCRResult, OCRLine, ProcessingContext, ExtractedField и ProcessingResult. Только стандартная библиотека Python.
- engine.py: независимый DocumentEngine с передаваемым провайдером и пока единственным passport processor.
- mrz.py: изолированный TD3 parser/validator.
- dates.py: отдельное разрешение века и календарных дат.
- detection.py: проверка признаков поддерживаемого TD3.
- visual_dates.py: экспериментальный поиск даты выдачи по OCR-подписям.
- paddle_provider.py: адаптер, запускающий локальный worker. FastAPI не импортирует Paddle и не загружает модели при старте.
- paddle_worker.py: CPU inference по локальным весам, без вывода содержимого документов в логи.
- app/document_processing.py: небольшой слой между API, существующим JSON-хранилищем и независимым движком.

Другой provider может реализовать extract(path, context) -> OCRResult; API и форма останутся прежними. Облачных реализаций в проекте нет.

ProcessingContext содержит document_type, country_of_study (двухбуквенный код либо null), issuing_country (трёхбуквенный код либо null). Страны и университет не определяют алгоритм. Контекст не подменяет распознанную страну выдачи или гражданство. Правила отдельных стран не реализованы.

## Как попробовать в интерфейсе

1. Загрузите только тестовый JPG/PNG паспорта или синтетической MRZ.
2. Откройте «Проверить данные».
3. Нажмите «Распознать локально».
4. Исправьте распознанные значения, заполните пустые поля и даты.
5. Нажмите «Подтвердить данные».

Распознавание запускается явно, чтобы не обрабатывать уже существующие пользовательские uploads автоматически. Ручной ввод работает без OCR. Для PDF сохранены загрузка, просмотр, удаление и ручное подтверждение; автоматическое OCR PDF в этом эксперименте не реализовано.

После сохранения файла по-прежнему доступен ручной шаг needs_confirmation. По явному запуску OCR статус меняется на processing, затем needs_confirmation либо processing_error. Только ручной PUT подтверждения устанавливает verified. uploaded сохранён в модели как состояние будущего полного автоматического pipeline. Не реализованы фоновые очереди и автоматический OCR при загрузке.

Черновик хранится в поле extraction существующей записи data/uploads/index.json. Подтверждённые пользователем поля — отдельно в passport_data. Статусы и данные переживают перезапуск. Удаление паспорта удаляет всю запись, включая extraction. OCR не перезаписывает уже подтверждённый паспорт; замена или удаление файла во время обработки не восстанавливает старую запись.

Новый API: POST /api/documents/passport/process с document_id и необязательными country_of_study/issuing_country. GET /api/documents/passport/data возвращает подтверждённые поля или доступные поля черновика. Все поля формы остаются редактируемыми.

## MRZ и оценки

Поддерживается TD3: две строки по 44 символа. Парсер нормализует регистр, пробелы и варианты знака-разделителя; он не дописывает потерянные символы и не заменяет автоматически O на 0. Несколько найденных паспортных MRZ считаются неоднозначностью.

Проверяются структура, контрольные цифры номера, даты рождения, срока действия, optional data и composite. У пустого optional data допускается контрольный символ 0 или <. Парсер сохраняет признаки повреждения для dev-отчёта. Процессор не заполняет поля по одной строке: при недостаточных признаках возвращает unsupported_or_not_passport. Ошибка самого OCR-provider остаётся failed; это не классификация изображения.

Поля движка: surname, given_names, nationality, passport_number, date_of_birth, sex, expiry_date, issuing_country, date_of_issue. Для каждого есть value, confidence, source и needs_confirmation. Не найденное значение и неизвестная уверенность — null; source при этом unresolved. Извлечённые значения имеют source=mrz либо visual_ocr и всегда needs_confirmation=true. Ручные подтверждённые данные по-прежнему отдельно в passport_data; оценки OCR к ним не приписываются.

Confidence — оценка распознавания строки, предоставленная OCR, а не вероятность правильности конкретного паспортного поля и не оценка подлинности. Проверка контрольной цифры сама по себе не присваивает числовую уверенность.

MRZ кодирует даты как YYMMDD, без века. Сырые значения сохраняются в raw_dates. Модуль dates.py требует корректную контрольную цифру и календарную дату, затем перечисляет возможные века:

- DOB: не в будущем, возраст в полных годах от 0 до 125 включительно. Это широкий порог физической правдоподобности, не утверждение о возрасте студента.
- Expiry: от текущей даты минус 100 лет до плюс 20 лет, строго после хотя бы одной допустимой DOB. Широкое окно сохраняет неоднозначность старых документов; это явно выбранная эвристика извлечения, не универсальное паспортное правило и не правовая проверка. Неоднозначную DOB не сокращаем до удобного для expiry варианта.
- Только один кандидат даёт value. Два или ни одного — value=null с причиной. Для дат вне выбранного окна нужен ручной ввод.
- DateResolution содержит value, confidence, resolution_method, needs_confirmation, candidates и reasons. today можно передать явно для воспроизводимого теста. Даже однозначный результат пользователь обязан подтвердить.

Confidence наследуется от OCR-строки; если provider не даёт score, значение null. Выбранный век не получает выдуманный процент уверенности. Метод разрешения и MRZ checks отдельно объясняют структурные основания.

Общий результат движка: success / partial / failed / unsupported_or_not_passport. API также возвращает processing_status в extraction. Для неподдерживаемого изображения документ остаётся needs_confirmation, чтобы ручной ввод работал. success означает полноту извлечения, никогда не verified.

Проверка типа требует две полные строки TD3, ожидаемые позиции второй строки и хотя бы одну прошедшую контрольную цифру номера/DOB/expiry. Длина 42–46 помогает назвать причину partial_or_damaged_td3, но потерянные символы не дописываются. Опечатка вроде UT0 допускается только для классификации; поле nationality при этом пустое. Повреждённый настоящий паспорт может не пройти эту ограниченную проверку — сообщение не является вердиктом о документе.

## Дата выдачи — experimental, с координатами

PaddleOCR worker теперь сохраняет bbox каждого блока: left, top, right, bottom в пикселях изображения. Провайдер передаёт их через OCRLine без изменений сортировки и MRZ-парсера. Используется тот же локальный OCR; новых зависимостей нет.

Подписи: Date of issue, Issue date, Date issued, Issued on, Дата выдачи и существующие французские/испанские варианты. Словарь ISSUE_LABELS можно расширять; extract_issue_date также принимает label_aliases. Разрешена одна ошибка символа в длинной подписи; это отдельно отмечается в диагностике. Английская OCR-модель не гарантирует распознавание иных языков.

Связь с датой проверяется в том же блоке, справа или ниже подписи. Для разных блоков используются bbox, а не порядок строк: текст соседней колонки между подписью и значением больше не мешает. Расстояния нормализованы по большей высоте пары блоков. Справа допускается зазор до 12 высот и смещение центров до 0.75 высоты; ниже — до 3 высот при перекрытии по горизонтали либо близком левом крае. Эти пороги — общие эвристики, не координаты шаблона. У text-only providers сохранён ограниченный fallback для соседних строк «только подпись» и «только дата»; при наличии bbox такой fallback не применяется.

Каждый кандидат содержит raw_text, normalized_date (либо null), possible_dates, distance_to_label, relative_position, ocr_confidence, matched_label, confidence, association_cost и причины сомнений. Distance — нормализованное геометрическое расстояние; cost дополнительно учитывает положение ниже (+0.2) и опечатку подписи (+0.4). Это не процент уверенности. Для выбора нужен отрыв от конкурента минимум 0.75; равные/близкие варианты остаются unresolved. Даже слабый конкурент учитывается, чтобы не выбирать удобную дату вслепую.

Совпадение с известной DOB/expiry, противоречие датам или более близкая подпись рождения/окончания исключают кандидата. Дата выдачи в день рождения теоретически возможна, но данный консервативный MVP оставляет такой случай для ручного ввода.

Основной порог OCR-score подписи и даты остаётся 0.90. Для score подписи 0.88–0.90 действует только отдельное узкое правило, описанное ниже. Отсутствующий score не придумывается. Выбранный результат имеет source=visual_ocr и needs_confirmation=true. Геометрия сама по себе не доказывает правильность текста.

Форматы: DD.MM.YYYY, DD/MM/YYYY, YYYY-MM-DD, DD MM YYYY (включая повторные пробелы), DD.MM.YY. Неоднозначный порядок дня и месяца остаётся неразрешённым. Для двухзначного года требуется известная DOB: перечисляются все годы между DOB и сегодня, дополнительно до expiry, если она известна. Только один возможный результат разрешает век; иначе null. Добавлен compact DDMMYYYY: весь блок после обрезки внешних пробелов должен состоять ровно из восьми ASCII-цифр. Нужны однозначная календарная дата, близкая пространственная связь с подписью справа/ниже (не дальше одной высоты текста) и отсутствие совпадения с DOB/expiry. Неоднозначный порядок дня/месяца остаётся unresolved; например 01022020 не выбирается автоматически.

Сохранённая extraction содержит visual_date_candidates и visual_date_debug (подписи, выбранный кандидат, причина выбора). Сводка production UI не включает эти объекты. Ручные поля не перезаписываются, verified возможен только после подтверждения пользователя.

52 unit/API-теста прошли: 18 layout, 7 дат, 8 intelligence, 9 MRZ, 10 API. Прошли обычный браузерный сценарий и сценарий с настоящим локальным OCR, ручным подтверждением, persistence, повторным OCR и unsupported fallback.

Ограничения: сложные/повёрнутые макеты, слитые блоки, пропущенные подписи, даты словами и уверенно неверные OCR-цифры могут мешать выбору. Совпадение структуры или высокий score не подтверждают правильность и подлинность документа. При сомнении нужен ручной ввод.

При установке в другом окружении сначала зафиксируйте его текущие зависимости, проверьте dry-run с constraints и только затем устанавливайте. Не используйте force reinstall или принудительные downgrade. Если есть конфликт, остановитесь и используйте отдельный согласованный OCR environment/process.

Пример для нового окружения с уже установленным NAVIAR:

```powershell
New-Item -ItemType Directory -Path .document-lab -Force
.\.venv\Scripts\python.exe -m pip freeze | Out-File .document-lab/baseline-constraints.txt -Encoding ascii
.\.venv\Scripts\python.exe -m pip install --dry-run -c .document-lab/baseline-constraints.txt -r requirements-ocr.txt
# Выполнять только если dry-run не меняет существующие пакеты и не выявил конфликтов:
.\.venv\Scripts\python.exe -m pip install -c .document-lab/baseline-constraints.txt -r requirements-ocr.txt
.\.venv\Scripts\python.exe -m scripts.download_ocr_models
```

Первичная установка пакетов и скачивание официальных весов требуют интернета. Это отдельный этап настройки: пользовательские изображения в нём не читаются и не отправляются.

Для CPU используются небольшие официальные модели PP-OCRv5_mobile_det и en_PP-OCRv5_mobile_rec. Репозиторий PaddleOCR не клонируется. GPU, облачные API и платные сервисы не нужны.

## Безопасность и ограничения

- Веса, промежуточные файлы, отчёты и синтетические изображения находятся в игнорируемой .document-lab/.
- Рабочие OCR-результаты записываются во временный каталог и удаляются после чтения.
- Worker получает только локальный путь, использует device=cpu и локальные model_dir.
- Отключены проверки источников моделей, telemetry Hugging Face и онлайн-режим Hugging Face; выставлен DO_NOT_TRACK.
- Python-сетевые операции запрещены audit hook в отдельном worker. Это ограничение процесса приложения, не полноценная изоляция ОС или firewall для произвольного нативного кода.
- stdout/stderr OCR-worker не попадают в логи FastAPI. Ошибки наружу возвращаются кодами, без текста документа или серверных путей.
- Изображение ограничено 20 млн пикселей, обработка — 120 секундами. Модели загружаются заново в каждом worker: это проще для экспериментального MVP, но медленнее постоянного OCR-сервиса.
- Нет гарантий распознавания наклонённых, размытых или плохо освещённых изображений, расширенных номеров TD3, TD1/TD2 и нестандартных паспортов.
- Нет OCR для визы, миграционной карты и регистрации.
- Нет проверки подлинности, биометрии, face matching и юридических решений.
- После аварийного завершения сервера статус processing может остаться в индексе; ручное подтверждение остаётся доступным.
- Сохраняются прежние ограничения single-user MVP: нет авторизации, шифрования, production-хранилища и надёжного стирания с физического диска. Реальные документы запрещены.

## Проверка v0.2 на синтетике

Локальный CPU-прогон synthetic-td3-issue.png: **10.683 с**, detected_document_type=td3_passport, status=partial. Получены DOB=2000-01-01, expiry=2030-01-01, date_of_issue=2020-01-15.
