# University Rules Engine — РУДН cleanup v1.1.0

> Текущий интерфейс медицинской категории использует три фиксированных слота; описание прежнего multi-file этапа ниже — история. Актуальная документация: [Медицинские сертификаты](medical-certificates.md). Rules Engine на этом этапе не менялся.

Локальный прототип планирования по опубликованным процедурам. Это не правовое заключение, не гарантия продления документов и не production-система. Только тестовые данные. Автоматических запросов к сайтам, scraping, AI, Visa OCR и внешних API нет.

## Основные файлы

- app/deadlines/models.py — DeadlineRule / UniversityProcedure, StudentContext, DocumentDates, MedicalExamination, Fingerprinting, Insurance / DMS, ServiceLocation, DeadlinePolicy.
- app/deadlines/calendar.py — BusinessCalendar с отдельными данными каждого года.
- app/deadlines/engine.py — calculate_deadline(rule, trigger_date, calendar), независимый от РУДН, UI, OCR и хранения.
- app/deadlines/rules.py — загрузка активной версии, подбор по университету, категории и режиму въезда; TKM определяется из гражданства.
- app/deadline_api.py — API и локальное сохранение тестового контекста.
- app/static/deadlines.js — форма дат, карточки, источники и список подготовки. Это русскоязычный прототип блока; существующий выбор RU/EN остального приложения сохранён.
- config/rules/manifest.json — активные версии; config/rules/rudn/1.0.0.json — историческая версия, config/rules/rudn/1.1.0.json — активная версия правил. Не редактируйте старую версию после выпуска: создавайте новую и меняйте manifest.
- config/deadline_policy.json — пороги urgent/attention и срок актуальности источников.
- config/calendars/RU/2026.json — официальный федеральный календарь пятидневной недели.
- config/service_locations.json — только МФЦ РУДН, с официальной страницей контактов. Клиники не добавлялись.

Все перечисленные пользовательские поля правил представлены в модели. Не подтверждённые адреса, сроки, места и другие значения имеют null; нулевой рекомендованный запас означает, что дополнительный срок не назначен.

## Правила и результаты проверки источников 29.09.2026

1. Визовый срок: по явно выбранному требованию проекта активировано 20 рабочих дней до окончания визы, источник — EN-страница РУДН (повторно просмотрена 29.09.2026). Это продуктовый выбор источника, а не новое подтверждение МФЦ. Историческое расхождение с RU-страницей (30 дней) сохранено в версии 1.0.0 и related_sources; пользовательское окно его не повторяет. Общий планировочный срок показывается визовому иностранному студенту РУДН; опубликованный перечень для многократной визы показывается только для явно выбранного сценария TKM + visa_required + foreign_student + rudn + multiple_entry. Для остальных сценариев список требует уточнения. Срок обработки — отдельное значение, результат продления не обещается.
2. Безвизовое продление: справочник МФЦ указывает 20 рабочих дней; новое сообщение РУДН различает продление срока пребывания за 20 календарных дней и цифровой миграционный учёт с особыми категориями. Нельзя объединять эти процедуры. Seed заблокирован до уточнения применимости и актуального срока.
3. Миграционный учёт после получения новой многократной учебной визы: 3 рабочих дня; правило активно только для иностранного студента с визовым режимом, указанной многократной визой и проживанием в общежитии университета. Дата получения вводится отдельно от даты выдачи. Шесть основных документов, дополнительная копия документа родителя только для несовершеннолетнего. При неизвестном возрасте показывается необходимость уточнения дополнения.
4. Медосвидетельствование: кандидат 30 календарных дней после въезда с 01.09.2026. Страница МФЦ и страница клиники описывают разные сроки/исключения; конкретная применимость не подтверждена. Seed заблокирован, точная дата не выдаётся. trigger_valid_from отдельно исключает события до 01.09.2026 даже после возможного подтверждения правила в будущем. Не назначены сроки повторного обследования, дактилоскопии или ДМС.

## Как считаются дни

День события исключается из отсчёта. before идёт назад, after — вперёд. Для business_days учитываются только рабочие даты федеральной пятидневной недели. Для calendar_days считаются все дни, без автоматического переноса крайней даты с выходного: такого универсального правила источники не подтверждают. Порядок включения дня события — внутренняя конвенция прототипа, которую следует сверить для конкретной процедуры в МФЦ.

Календарь содержит обычные выходные (суббота/воскресенье), явные праздничные даты и утверждённые нерабочие переносы. Есть поле working_weekends для будущих календарей; в 2026 список пуст. Переносы не выводятся алгоритмом. Работа МФЦ в субботу не делает субботу рабочим днём для такого расчёта.

Основание январских переносов — [постановление Правительства №1466 от 24.09.2025](https://static.government.ru/media/files/4jeB8hNKm69ggOa9yDiYOli6YoAyM21i.pdf). Перечень праздников, 9 марта и 11 мая сверены с [календарём Минтруда](https://mintrud.gov.ru/social/social/1366); указанные в его публикации предлагаемые январские переносы подтверждены итоговым постановлением. Данные сохранены явно, отдельно от кода.

Если нужного года нет, business-day сдвиг возвращает deadline_date=null, status=unknown, reason=calendar_missing:YYYY. Переход через Новый год требует данных обоих лет. Календарный срок при этом может быть вычислен, но неизвестный остаток рабочих дней будет null с предупреждением. Региональные праздники и специальные графики не поддерживаются.

Остатки считаются относительно server today (локальная дата сервера). days_remaining_business — знаковый подсчёт, исключающий раннюю границу и включающий позднюю. Overdue/due_today определяются по календарной дате даже в выходной. Базис остальных визуальных статусов задаётся policy.status_day_type; начальные пороги 3 и 10 дней. Рекомендованный запас, если задан, вычитается в календарных днях отдельно и не меняет deadline_date.

Источник старше 90 дней (порог конфигурируется) либо с будущей датой проверки получает rule_source.status=needs_reverification. Сам расчёт возвращает status=unknown и пустую крайнюю дату. Последняя проверка означает просмотр источника разработчиком, а не обещание, что правило никогда не изменится.

Пример активного расчёта визы: 30.10.2026 минус 20 рабочих дней = 02.10.2026. На 29.09.2026 до неё 3 рабочих дня. До самого окончания визы на эту дату 31 календарный день (не 32). Для подтверждённого сценария новой визы: получение 29.09.2026 плюс 3 рабочих дня = 02.10.2026.

## Dev UI и локальное хранение

Эта большая ручная форма теперь доступна только в ?dev=1. Обычный dashboard получает результаты через [StudentContext](student-context.md), не из data/planning. В dev-панели сохранены блок «Сроки и действия», сворачиваемая форма дат/условий, медицинская категория и диалог «Что подготовить». Университет и гражданство берутся из существующего профиля; остальные условия студент указывает явно. На другой университет или гражданство прежние данные формы автоматически не переносятся.

GET /api/deadlines/state читает контекст. PUT сохраняет и считает; POST /api/deadlines/calculate считает без записи. Хранение: data/planning/context.json, атомарная замена под блокировкой, один worker. Папка исключена из Git. Контекст не записывается в localStorage и не содержит файлов документов. При изменении дат повторное сохранение заменяет предыдущие значения, пустые даты очищают их.

Даты планирования отделены от файлов документов и OCR: удаление загруженного файла не удаляет вручную введённые даты процедуры. На этом этапе их нужно исправлять отдельно. Логика passport_data и verified не изменялась; добавлен тип загрузки medical_certificates, исходные пользовательские файлы не менялись. Нет авторизации/изоляции студентов/шифрования: хранилище общее для локальной демоверсии. Реальные данные запрещены.

## Медицинские данные и пятая карточка

MedicalCertificates (алиас MedicalDocuments) содержит status, completed_at, valid_until, next_required_at, days_remaining, files[]. Даты вводятся вручную и подтверждаются флажком. Дата прохождения не может быть в будущем, valid_until не может предшествовать completed_at. Неподтверждённые даты сохраняются как черновик и не используются как подтверждённый срок.

valid_until — указанная пользователем дата окончания сертификатов, не автоматически вычисленная периодичность обследования. При подтверждении backend считает days_remaining. next_required_at берётся только из правила medical_renewal; сейчас оно заблокировано до уточнения применимости и периода, поэтому «Обновить до: Требуется уточнение». offset=0 у этого неактивного правила — placeholder, не медицинский срок. MedicalExamination, Fingerprinting и Insurance/DMS — отдельные модели. У Fingerprinting четыре явных состояния без выдуманной периодичности. Insurance содержит provider, policy_number, valid_from, valid_until, days_remaining, status; остаток рассчитывает backend по указанной valid_until. Отдельного UI ДМС и дактилоскопии пока нет.

Пятая карточка: медицинские сертификаты, прежние ограничения JPG/JPEG/PNG/PDF и 10 МБ на файл, preview перед отправкой, имена и размеры в списке, просмотр, замена и удаление отдельных файлов. Desktop — 3 + 2, mobile — одна колонка. Каждый файл добавляется отдельным bounded multipart-запросом; категория допускает несколько файлов. Подтипы: medical_exam_certificate, additional_medical_certificate, other_supported_medical_document. Они не добавляют новые категории в счётчик: один или несколько медицинских файлов дают 1 из 5.

В общем index.json только medical_certificates хранится массивом записей; остальные четыре категории сохраняют прежний формат. Старый одиночный медицинский record нормализуется при чтении в памяти без записи, при следующей мутации сохраняется массив. Исходные имена — только подписи; серверные имена UUID и allowlist расширений. GET /api/documents возвращает плоский список записей файлов с type=medical_certificates, document_id, medical_type, name, size, url. files[] в результате планирования содержит ID существующих медицинских файлов.

POST /api/documents/medical_certificates?medical_type=... добавляет файл. GET /api/documents/medical_certificates/{id}/file просматривает его, PUT /api/documents/medical_certificates/{id} заменяет, DELETE /api/documents/medical_certificates/{id} удаляет. Замена получает новый ID; старый URL перестаёт работать. DELETE всей категории запрещён, чтобы случайно не удалить другие сертификаты. Проверка содержимого и ограничения общие с прежним upload pipeline; при замене/удалении используется прежняя блокировка и атомарная запись индекса, с откатом при ошибке записи. Это не полноценная транзакционная БД: прежнее ограничение одним worker и отсутствие защиты от аварийного отключения/сбоев диска сохраняются.

OCR медицинских документов отсутствует. Даты не удаляются при удалении файла и остаются отдельными ручными данными; files[] строится из фактических загрузок. Подтип не доказывает содержание или действительность документа. data/uploads и data/planning по-прежнему исключены из Git.


Модальное окно содержит действие, дату, остаток дней, место, применимый перечень и один официальный источник. Внизу один текст о проверке актуальности. История источников остаётся в конфигурации и здесь.

Нужно подтвердить применимость первичного и повторного медосвидетельствования к категориям студентов, срок обновления после прохождения, исключения, официальные места и цены. Не добавлены клиники и новые медицинские сроки.

Итог cleanup: 95 серверных тестов прошли. Браузерные сценарии с локальным OCR и без него прошли: TKM, визовые сроки, медицинские даты и refresh, пять категорий, счётчик 0–5, просмотр/удаление, старые четыре категории, ручное подтверждение, повторный OCR и неподдерживаемое изображение. Исходные uploads сверены по SHA-256 без изменений. Зависимости не добавлены.

## Точечная UI-регрессия

У dashboard-title удалены tabindex=-1 и безусловный focus(). При обычной загрузке браузер сохраняет естественный порядок фокуса, поэтому неинтерактивный заголовок не обводится рамкой. Стили focus-visible интерактивных элементов сохранены; для input явно используется тот же контур.

Добавлены серверные проверки трёх форматов и подтипов, нескольких файлов после перезапуска, удаления только выбранного файла, замены и отката при ошибке записи, совместимости старого индекса, запрета удаления категории целиком, недопустимых типов/ID/путей и размера. Браузер проверяет три refresh, keyboard focus, mobile-колонку и desktop 3 + 2, несколько медицинских файлов, preview/размер/просмотр/обновление/удаление, 4/5 → 5/5 и прежний Passport OCR.

Итог multi-file этапа: 106 серверных тестов и оба браузерных сценария прошли, включая реальный локальный Passport OCR. Исходные uploads не изменены.
