# StudentContext и Next Actions v0.1

## Основные файлы

- app/student_context.py — ContextField и единый StudentContext для обычного dashboard; build_context собирает источники, rule_results адаптирует подтверждённые значения к прежнему движку сроков.
- app/student_api.py — профиль и точечное подтверждение одного поля документа.
- app/next_actions.py — NextAction и детерминированный выбор 1–3 приоритетных действий.
- app/static/student.js — результатный dashboard и однополевая fallback-форма.
- app/static/deadlines.js — прежний интерфейс ручного тестирования только в ?dev=1.

Старый StudentContext из app/deadlines/models.py остаётся внутренним контрактом входных значений Rules Engine. Новый модуль импортирует его как RulesContext. UI не строит этот контракт из DOM или localStorage в обычном режиме.

## Источники и приоритет

ContextField содержит value, source, confirmed, confidence и status. Пустое значение — null/missing, не вымышленная дата. confidence не назначается вручную как 0.99: для ручных значений это null. Разрешены источники profile, document_record, passport_ocr, visa_ocr, migration_card_ocr, registration_ocr, medical_document, derived_rule, manual_fallback, manual_confirmed. document_record нужен для метаданных файла: они не выдаются за результат OCR.

Профиль — один исходный серверный файл data/student/profile.json. Он содержит случайный стабильный student_id и четыре поля onboarding. При первом открытии старый профиль браузера переносится, если серверного ещё нет; после успешного восстановления старый localStorage ключ удаляется. Уже существующий серверный профиль имеет приоритет. ID не является авторизацией; приложение по-прежнему single-user.

Номера, даты и другие документные поля не копируются в профиль. StudentContext вычисляется при чтении поверх data/uploads/index.json. Документы остаются source records. GET /api/student/context возвращает context, список документов для карточек, результаты правил и next_actions. Snapshot не сохраняется в отдельный JSON.

Автоматически собираются гражданство (коды профиля нормализуются в TKM/UZB/TJK/KGZ/KAZ), университет, ступень и язык, данные подтверждённого паспорта, ID документов, наличие трёх медицинских файлов и их ручные даты. TKM → visa_required берётся из существующей конфигурации. Категория foreign_student выводится из выбранного известного иностранного гражданства в студенческом профиле; для «Другое» остаётся неизвестной. Возрастная категория для правил выводится только из подтверждённой даты рождения.

Подтверждённый passport_data приоритетнее extraction. Если значение отличается от OCR или введено без OCR, source=manual_confirmed. Для совпадающего подтверждённого поля сохраняется source=passport_ocr и исходная confidence. Issuing country из MRZ доступна как неподтверждённый OCR-кандидат: отдельного подтверждения этого поля в старой форме нет. Это не подтверждение подлинности паспорта.

Для будущих OCR предусмотрено чтение extracted_fields, но никакой новый OCR не реализован. Такие значения остаются needs_confirmation и не участвуют в расчётах до ручного подтверждения. manual_fields с confirmed=true имеют высший приоритет. Автоматических вызовов OCR нет.

## Fallback и даты

В обычном интерфейсе есть локальные запросы: дата окончания визы, дата въезда, дата окончания регистрации. Если файла нет, сначала открывается существующая загрузка. Если файл есть, открывается одна дата и кнопка «Подтвердить». После подтверждения дата сохраняется в manual_fields исходного документа, source=manual_fallback. ID в запросе защищает от сохранения старой формы в заменённый файл; при удалении файла исчезают и его fallback-данные. Даты можно исправить тем же способом.

PATCH /api/student/documents/{kind}/{document_id}/field принимает field, value, confirmed=true. Backend ограничивает поля по типу документа, проверяет даты и порядок issue/expiry. Даты выдачи/въезда/получения не допускаются в будущем. Ошибки валидации не возвращают присланные значения. Паспорт использует прежнее подтверждение всех полей, медицинские файлы — прежние отдельные формы дат.

Тип визы, дата её получения, residence_type и другие ещё не определённые условия не угадываются. API допускает подтверждение перечисленных полей соответствующего документа, но основной однополевой UI сейчас сфокусирован на трёх датах. Место проживания пока null; процедура учёта после новой визы остаётся неопределённой без её условий. Registration expiry не переименовывается в stay_expiry: это разные понятия. Медицинские issue_date не превращаются автоматически в дату прохождения всей процедуры. Периодичность обследований не придумана.

## Next Actions и dashboard

В обычном dashboard нет селекторов режима въезда, категории, возраста и технических параметров правил. Он показывает карточки результатов и локальные запросы недостающих дат, а блок следующего шага — до трёх действий. Настоящие deadlines создаются только из результатов Rules Engine с известной датой и применимостью. Приоритет: overdue, due_today, urgent, attention, missing, safe; внутри приоритета ближайшая дата раньше. Неопределённые и устаревшие правила не превращаются в точный срок.

NextAction: title, priority, reason, deadline, days_remaining, destination, source_rule, а также document_type/field для перехода к нужному документу. Пример на фиксированную тестовую дату 29.09.2026: профиль TKM + РУДН и подтверждённая дата окончания визы 30.10.2026 дают «Подать документы на продление визы», priority=urgent, deadline=2026-10-02, days_remaining=3 рабочих дня, destination=МФЦ РУДН, source_rule= rudn.visa_extension v1.1.0. В работающем приложении используется текущая дата сервера, пример не захардкожен.

Медицинская кнопка: 0/3 → «+ Добавить сертификаты», 1/3–2/3 → «Продолжить загрузку», 3/3 → «Управлять». Три цветных слота и все операции сохранены.

## Dev mode и ограничения

http://127.0.0.1:8000/?dev=1 включает прежнюю форму для исследования Rules Engine. Она сохраняет своё состояние в data/planning/ и не влияет на обычный StudentContext. Это переключатель интерфейса локального MVP, не авторизационная защита endpoint-ов. Ссылки на него нет в основной навигации.

Нет авторизации, разделения студентов и шифрования; профиль общий для этого локального сервера. Только вымышленные данные. data/student/, uploads и planning исключены из Git. Новых зависимостей, AI, Visa/Migration/Registration/Medical OCR, университетов и языков нет.

## Проверки

122 уникальных серверных теста; прежние MRZ, Passport Intelligence, документы, Deadline Engine и University Rules Engine сохранены. Новые тесты проверяют сбор профиля/паспорта, источники, ручной приоритет, неподтверждённый OCR, стабильный student_id, отсутствие дублирующего read-model на диске, удаление/замену документа, медицинские даты, ранжирование NextAction и независимость от dev-состояния.

Оба браузерных сценария прошли, включая реальный локальный Passport OCR, повторный OCR и ручное подтверждение. Проверены обычный dashboard без большой формы, работа dev-панели, однополевая дата визы, автоматический deadline, refresh, состояния медицинской кнопки и мобильный layout.
