# Visa Intelligence v0.1

Это локальный single-user MVP. Использовать только синтетические изображения и явно демонстрационные specimens. Реальные визы и персональные данные загружать нельзя. Авторизации, шифрования хранилища и production-изоляции пользователей нет.

## Сценарий

Загрузить JPG/PNG в существующую карточку «Виза» → «Проверить данные» → «Распознать локально» → проверить поля → «Подтвердить данные». Можно исправить подтверждённую форму и подтвердить повторно. PDF хранится и просматривается через прежний upload pipeline; для него пока доступен ручной ввод.

Форма содержит номер, тип, кратность, дату выдачи, начало и окончание действия. Дополнительные поля раскрываются, если OCR нашёл значения: гражданство, номер паспорта, цель поездки и орган выдачи. Пустые поля имеют локальную подсказку «Указать вручную». Неизвестные поля разрешено оставить пустыми: система не заставляет придумывать даты. Для deadline нужна подтверждённая valid_until.

OCR заполняет только пустые поля открытой формы. Ручные правки не сохраняются до подтверждения и могут потеряться при закрытии формы; результат OCR сохраняется и переживает refresh. Повторное распознавание подтверждённой записи запрещено. Подтверждение во время параллельного OCR имеет приоритет. document_id защищает от подтверждения удалённого/заменённого файла.

## Модель и API

В app/visa_engine/ находятся модели, словари нормализации, визуальный поиск, отдельный MRV parser и orchestration. Passport TD3 и provider не изменены. Используется тот же PaddleOCRProvider, локальные CPU-модели и ограничения изображений.

Каждое поле содержит value, source (mrz/visual_ocr/manual/unresolved), confidence и needs_confirmation. До подтверждения needs_confirmation=true; verified появляется только по PUT пользователя. Confidence — оценка OCR и пространственной связи, не вероятность подлинности или юридической действительности.

- GET /api/documents/visa/data — значения и краткий результат обработки.
- POST /api/documents/visa/process — document_id; локальная обработка изображения.
- PUT /api/documents/visa/data — document_id и data; валидация и подтверждение.
- Удаление/просмотр/загрузка используют прежние /api/documents/visa endpoints.

Поля и диагностический результат находятся в исходной записи визы data/uploads/index.json: visa_extraction (OCR), visa_data (подтверждённые значения), visa_fields (происхождение подтверждённых значений). Файлы остаются под безопасными UUID-именами вне static. uploads и Document Lab исключены из Git. OCR-блоки/кандидаты не возвращаются в production UI. Данные не помещаются в browser storage и не выводятся в серверные логи.

## Извлечение

Поиск использует словарь подписей, OCR confidence и bounding boxes. Значение справа/снизу должно принадлежать своей подписи, а не более близкой конкурирующей подписи. Дата рождения участвует как блокирующий label. Несколько разных подходящих значений оставляют поле unresolved. Пространственные расстояния нормированы высотой текста, координат шаблона нет.

Поддержаны DD.MM.YYYY, DD/MM/YYYY, YYYY-MM-DD, DDMMYYYY и DD MM YYYY с явно заданным порядком день-месяц-год. DD.MM.YY распознаётся как формат, но без явного полного года остаётся unresolved. В текущем потоке для таких визуальных дат век не угадывается. Даты проверяются календарно; противоречащий порядок дат снимает автозаполнение дат.

Entries и visa_type имеют отдельные многоязычные словари. Неизвестная/неоднозначная категория остаётся unknown в форме (null/unresolved в извлечении). Один код вроде C не превращается в student. Подписи на русском предусмотрены, но установленный recognizer английский: качество кириллицы не заявляется.

Поддержанная виза определяется по структурно согласованной MRZ либо сочетанию визовых подписей, номера, дат и категории/кратности. Это эвристика для выбора обработчика, не классификатор всех виз мира. Остальное получает unsupported_or_not_visa и ручной fallback.

## MRZ

Отдельный parser поддерживает MRV-A (две строки по 44 символа) и MRV-B (по 36), по [ICAO Doc 9303 Part 7](https://www.icao.int/sites/default/files/publications/DocSeries/9303_p7_cons_en.pdf). Контрольные цифры — только проверка структуры распознанного текста. Пропущенные символы не достраиваются.

Номер MRZ неоднозначен: он может быть номером визы или паспорта. Назначение выбирается только при совпадении с подписанным визуальным полем. Для срока YYMMDD требуется совпадающая полная визуальная дата: без неё век не определяется. Гражданство может браться из MRZ напрямую при достаточном OCR confidence. Дата выдачи, valid_from, тип и кратность из MRZ не выдумываются. Имя и DOB в пользовательскую модель визы не копируются.

## StudentContext и сроки

StudentContext собирается из исходной записи, без отдельного сохранения копии. visa.valid_until отображается также как visa.expiry_date для совместимости существующего адаптера сроков. До подтверждения OCR-значения не создают deadline. После подтверждения неизменённое OCR-поле имеет source=visa_ocr, исправленное — manual_confirmed. Исходный mrz/visual_ocr остаётся в visa_fields. Старые подтверждённые даты из manual_fields сохраняют приоритет до новой полной проверки.

Rules Engine, университетские правила и календарь не изменены. Адаптер переводит entries=multiple в прежнее rules-поле visa_type=multiple_entry. Дата valid_until передаётся как visa_expiry. Событие обновления документа заново получает StudentContext, сроки и Next Actions.

Синтетический пример: RUDN + TKM, valid_until=2026-10-30 → дата подачи 2026-10-02 в текущем календаре/правиле. Расчёт по-прежнему ограничен доступным календарём и актуальностью источников, ничего не экстраполируется на неподдержанный год.

## Document Lab и проверки

```powershell
.\.venv\Scripts\python.exe -m scripts.document_lab --synthetic --generate --document-type visa
.\.venv\Scripts\python.exe -m unittest discover -s tests
.\.venv\Scripts\python.exe tests/run_browser_tests.py
.\.venv\Scripts\python.exe tests/run_browser_tests.py --ocr
```

scripts/visa_fixture.py создаёт только SYNTHETIC TEST ONLY изображение; оно и отчёт лежат в игнорируемой .document-lab/. Отчёт содержит detected_document_type, mrz_found/format, OCR blocks, extracted_fields, sources/confidence, date/entries/type candidates, reasons, processing_seconds и errors. Никакого нового внешнего сервиса или зависимости.

Тесты изолируют uploads/profile/planning от рабочих данных. Обычный браузерный прогон использует синтетический provider для визы; --ocr использует настоящий установленный локальный provider и для паспорта, и для визы. Проверяются повторное OCR, ручные правки, подтверждение, сроки/Next Actions, refresh, unsupported fallback, медицинские слоты, старые документы и keyboard focus.

## Результат локального эксперимента

Синтетическая виза: TEST00001; student; multiple; issue_date=2026-09-15; valid_from=2026-09-16; valid_until=2026-10-30. Шесть основных полей распознаны через visual_ocr, needs_confirmation=true. Confidence основных полей примерно 0.75–0.84: оценка учитывает расстояние от подписи.

В реальных OCR-прогонах строки MRZ потеряли символы и не использовались. MRV-A/B отдельно проверяются на корректных синтетических строках. Дополнительный номер паспорта DEMO00002 OCR прочитал как DEM000002 — пример необходимости проверки каждого поля. Не исправляем O/0 догадкой.

Сравнение последовательных прогонов на этом компьютере: виза 14.311 с, паспорт 7.926 с. Итоговый повтор после уточнения синтетической MRV-строки: 11.084 с, те же шесть основных полей успешно получены из visual_ocr. Виза содержит 19 OCR-блоков и изображение 1750×1140 против меньшего паспортного fixture. Это одиночный замер, не benchmark: размер, число блоков, запуск отдельного CPU-процесса и загрузка моделей влияют на время. Визовый parser не запускает второй OCR.

Ограничения: нет проверки на настоящих визах, поворот/блики/печати и другие макеты могут дать unresolved; только JPG/PNG OCR; повреждённая MRZ и неоднозначный век не восстанавливаются. Юридическое значение «valid until» различается между странами: приложение использует текущие правила РУДН, не обобщает их на все визы мира. Реальные документы использовать нельзя.

# Visa Intelligence v0.2 — low-resolution / partial detection

Preprocessing включён только для VisaEngine в приложении и Document Lab. Passport OCR/provider/worker, Rules Engine и StudentContext не изменены. Новых зависимостей нет.

- Наибольшая сторона до 600 px → OCR-копия 3x; до 900 px → 2x; больше → исходный масштаб. Lanczos, без изменения пропорций, резкости, контраста и бинаризации. Bbox пересчитываются к исходному размеру.
- При признаках MRZ/визы и неудачном строгом MRV-разборе — одна дополнительная попытка на нижнем crop. Его границы берутся из OCR-пары, иначе используется общая нижняя область. Нет координат конкретного паспорта/визы. Всего максимум два OCR-вызова.
- Временные копии удаляются через TemporaryDirectory, исходный upload не меняется. Ошибка crop не стирает результат visual OCR.
- MRZ whitelist A–Z, 0–9, < применяется как фильтр принятия строк после существующего recognizer. Словарь модели не меняется. Неизвестные символы/пропуски не «исправляются».
- Detection отдельно от извлечения полей: валидная MRV либо прежний сильный layout либо достаточная комбинация независимых признаков. Новая ветка возвращает supported_partial. Одинокого VISA и случайных дат/номеров недостаточно.
- Диагностический score 0–10 — сумма признаков, не probability/confidence поля. Для partial требуется минимум 6 баллов и комбинация: VISA + пространственно согласованная MRV-like пара + дата; либо VISA + ≥3 confident labels + ≥2 даты + хотя бы одно уверенное поле. Баллы сами по себе не обходят комбинацию.
- Обычный label-aware threshold 0.90 сохранён. Для уникального header serial справа от отдельного VISA есть узкий fallback: OCR номера ≥0.95, заголовка ≥0.90, убедительная связь в верхней группе, одна MRV-like пара независимо ниже, нет конкурирующего номера. Короткий соседний префикс и номер объединяются только при близкой геометрии. Date-like числа не используются как serial. Итоговая confidence снижена за расстояние и отсутствие явной подписи номера. Не применяется к документам без MRV-like evidence.
- Все OCR-поля требуют подтверждения. Пустые даты не участвуют в Deadline Engine. Диагностика/сырые блоки доступны только в локальном Lab, не в production UI API.

Публичный пример по ссылке пользователя побайтно совпал с [иллюстрацией статьи](https://myvisatorussia.com/ru/info/cel-poezdki-v-rossiyu/). Это публичная иллюстрация, не официальный маркированный SPECIMEN. Используется только локально в игнорируемой .document-lab/fixtures/russian-public-visa.jpg с provenance; не добавлена в Git. Полные OCR-блоки и bbox до/после: .document-lab/visa-v02/report.md; JSON: .document-lab/russian-public-visa-result.json.

Результат: 600×401 → OCR-копия 1800×1203; 29 → 41 блок. supported_partial, score=8/10. Одно основное поле — номер, source=visual_ocr, confidence=0.6997, needs_confirmation=true. Даты с двузначным годом, тип и кратность оставлены unresolved. Точных распознанных подписей этих полей нет. Номер предложен по уникальной верхней группе возле VISA, не по догадке из MRZ. Две нижние строки длиной 44 символа не соответствуют структуре поддержанного MRV: ошибки mrz_first_line_structure и mrz_second_line_structure. Crop не восстановил допустимую структуру; извлечения из MRZ нет.

Время одного прогона 20.043 с: visual 14.690 + crop 4.992 + подготовка/разбор. Дополнительное время — плата за увеличенную копию и второй OCR-вызов; это не статистический benchmark. Основные ограничения остаются: английский recognizer, слабое чтение мелкой кириллицы, неоднозначный век, только JPG/PNG OCR. Частичное определение типа не является проверкой документа.
